# 展示模型重构与思考块设计

> 状态：**2026-11-20 定稿；2026-11-25 增补第三个模式「极简」**——①思考块全文不截断、默认折叠 + 平铺开关、20 KB 单卡 + 思考续卡；②**实时预览已移除**（当天试验后放弃流式，见 [feishu-streaming-experiments.md](./feishu-streaming-experiments.md)）；③**档位合并**：`compact` 是模式（卡片拓扑），其余全部改为正交开关；**预设后来又被移除**（2026-11-20 使用者要求——预设行里出现了两个「详细」，与模式行重复、更乱）：卡上只有「模式 + 思考两开关 + 工具明细 + 工具输出 + 两个截断长度」。旧档位名只被读一次用于迁移默认值（`standard`→一行摘要、`verbose`→不截断），不再写回。仍未暴露在 Web GUI 设置页（只有命令与卡片，见 TODO）。极简模式的形态、约束与取舍见第三节之后新增的「极简」小节与第十节决策记录。落地时按本文验收，完成后同步 [架构](<./architecture.md>)、[首页](<../README.md>) 与 [变更记录](<../CHANGELOG.md>)。
> 关联：[`src/display-level.ts`](<../src/display-level.ts>)（档位→policy）、[`src/feishu-streaming.ts`](<../src/feishu-streaming.ts>)（步骤卡渲染）、[`src/feishu-display.ts`](<../src/feishu-display.ts>)（`/display` 卡）、[`src/commands.ts`](<../src/commands.ts>)（命令解析）、[`src/config.ts`](<../src/config.ts>)（设置项）、[`src/card-fold.ts`](<../src/card-fold.ts>)（折叠面板）、[`src/text-chunk.ts`](<../src/text-chunk.ts>)（分片/截断）、[飞书能力参考](<./feishu-capabilities.md>)（流式卡片）。

## 一、为什么改

当前四个档位（`compact` / `standard` / `detailed` / `verbose`）实际只是同一组轴的**预设**，各档取值如下：

| 轴 | compact | standard | detailed | verbose |
|---|---|---|---|---|
| 思考 | off | 首行预览 | 折叠 + 前 200 字 | 折叠 + 全文 |
| 工具 | off | 一行摘要 | 完整 | 完整 |
| 参数 / 结果 | 关 / 关 | 关 / 关 | 开 / 开 | 开 / 开 |
| 工具输出截断 | 截 | 截 | 截 | 不截（×4，封顶 6000） |
| 发哪些卡 | 回合卡 + 答案卡 | 每步一张 | 每步一张 | 每步一张 |

由此产生三个真实问题：

1. **耦合**：想「详细档的工具 + 完全展开的思考」做不到——参数/结果要么跟着全开，要么思考被砍到 200 字；
2. **死开关**：四个 `show*` 开关只能「减」，低档位下不生效，`/display` 卡必须隐藏它们并写一句「只在详细/完全展开生效」；
3. **custom 死角**：组合不落在任何档位时，卡片只能显示「当前组合不等于任何一档」——那不是能力，是语义漏洞。

## 二、目标模型：三个模式 + 正交开关

**模式只决定「发哪几张卡」**，不再决定「显示多少」：

| 模式 | 形态 | 说明 |
|---|---|---|
| 极简（`minimal`） | 一轮一张极简过程卡 + 一张答案卡 | 2026-11-25 新增：过程卡只留每步的 `💬` 回复和 `✅/❌/⏳` 工具说明行，其余全部不渲染；不按时钟刷新、不发 Turn Complete 卡 |
| 简洁（`compact`） | 一轮一张过程卡 + 一张答案卡 | **保持不变**：整体拓扑（`turnCard`、纯工具步不发卡、答案卡承载正文）不是开关能表达的，因此单独保留 |
| 详细（`detailed`） | 每一步一张卡 | 原 `standard` / `detailed` / `verbose` 三档合并到这里 |

**显示多少全部交给正交开关**，任意组合可达、没有死开关：

### 思考组

| 开关 | 取值 | 默认 | 说明 |
|---|---|---|---|
| 思考内容 | 显示 / 关 | 显示 | 关 = 卡上没有思考块（等价旧 `reasoning: off`） |
| 思考折叠 | **折叠 / 平铺** | **折叠** | 折叠 = 折叠面板、默认收起；平铺 = 正文直接铺在卡上（面板不出现）。**两个方向都保留**，默认折叠 |
| 思考预览 | 开 / 关 | **开** | 思考阶段在卡上显示「最后 N 字 + 🧠 正在思考中…」，详见第四节 |
| 预览长度 | 80–4000 字（设置项） | **200** | 复用现有 `reasoningPreviewChars` 键，语义改为「预览字符数」 |

### 工具组

| 开关 | 取值 | 默认 | 说明 |
|---|---|---|---|
| 工具明细 | 关 / 只报计数 / 一行摘要 / 完整 | 完整 | 关与计数只出现在简洁与旧 standard 的等价组合里 |
| 参数 | 开 / 关 | 开 | |
| 结果 | 开 / 关 | 开 | |
| 工具输出 | 截断 / 不截断（×4，封顶 6000） | 截断 | 进「更多」折叠区 |

其余保持不变：耗时刷新间隔（3/5/10/30 秒）、简洁档的工具行三选一、语言。

### 档位名降级为「一键预设」

四个名字都保留，但只是把上面这组开关设成某组值，**不再是独立概念**：

| 预设 | 模式 | 思考 | 工具 | 参数 / 结果 | 工具输出 |
|---|---|---|---|---|---|
| 简洁 | compact | 关 | 关 | 关 / 关 | 截断 |
| 标准 | detailed | 折叠 + 预览开 | 一行摘要 | 关 / 关 | 截断 |
| 详细 | detailed | 折叠 + 预览开 | 完整 | 开 / 开 | 截断 |
| 完全展开 | detailed | 折叠 + 预览开 | 完整 | 开 / 开 | 不截断 |

三个非简洁预设之间**只剩工具轴差异**（思考轴对它们相同）；要「平铺」就手动开，不进入预设。卡片上标「预设：标准 / 详细 / 完全展开」，手动改任一开关后改标「自定义」。

## 二之二、极简模式：过程卡只留回复与工具说明（2026-11-25）

**定位**：三种模式里卡片最少、API 最省的一种。一轮最多两张卡（过程卡 + 答案卡），纯回答回合只有答案卡；过程卡只有两类行，看的人不需要在过程里读结构。

### 卡上有什么

| 行 | 内容 | 取值/回退 |
|---|---|---|
| `💬` 回复 | 该步模型输出给用户的文字（旁白），**全文、保留换行、不截断** | 该步没写文字就没有这一行 |
| `✅/❌/⏳` 工具说明 | 每个工具调用的 `description`（模型为这次调用写的那句话）；`✅` 成功、`❌` 失败、`⏳` 运行中 | 没有 description 时用**预制动作名 + 它碰到的对象**：`✅ 读取 feishu-progress.ts`、`✅ 编辑 config.ts`、`✅ 搜索 renderMinimalProgressCard`；预制表里没有的工具回退成 `工具名 · 对象`，两者都没有就是工具名 |

- **没有**：步头/步号、相位图标（📡🧠✍️🔧）、分阶段耗时、参数、结果、PTC 子行、注入提示、思考块。
- **动作名是预制表，不是机翻**（`ZH_TOOL_ACTIONS` / `EN_TOOL_ACTIONS`，语言跟随插件）。起因（2026-11-25）：只列文件名看不出是 `read` 还是 `edit`；答案也不能退回工具名——`read` / `edit` 这种机器词在中文界面里读起来像噪声。表按语言给出动词（读取 / 编辑 / 搜索 / 发送文件……），跨语言一致，未收录的工具自动降级。对象由**极简专用的更宽派生**给出（文件名、shell 程序名、检索词、URL host），不动紧凑卡的行——紧凑只显示文件名/程序名。
- 实时状态与总耗时由**卡片标题**承担（`🐳 深度求索中 · 12.3s`），所以行里不再重复。
- 结束标题写轮次与**总步数**：`⚙️ 第 N 轮 · 12 步 · 12.3s`（失败 `第 N 轮失败 · 12 步`），不写工具数——使用者 2026-11-25 明确要求。

### 三条硬约束

1. **不按时钟刷新**：卡上没有时钟与相位，只有事件（回复/工具状态变化）才写卡；极简下不装运行时钟，也不推只为紧凑卡存在的相位/思考/注入/未执行标记写入。
2. **懒开卡**：`step/start` 只记步骤，第一行内容出现才建卡——否则先发出一张只有标题的空卡。
3. **不折叠、不按步数分页**：卡内容天然小。唯一例外是**字节安全阀**——整页渲染超过 16 KB（`PROGRESS_PAGE_MAX_BYTES`）时在**步边界**换页，一个步骤永远不被拆开；这是防止长回复把卡撑过飞书 ~30KB 上限，不是排版偏好。

### 两张卡的钱怎么省

- 没有 Turn Complete 卡：摘要折进承载答案的那张卡（`foldsSummaryIntoAnswerCard`，与紧凑一致）。
- 媒体不降级：回复里的图片/视频走与步骤卡/答案卡同一个 `cardImages.hydrate`，真的内联；没有 hydrator 的部署才回退成 `🖼 路径` 文字（关键坑 39 的保护网）。
- PTC：程序派发的内层调用没有自己的 description，所以只渲染 `run_code` 程序那一行（它的 description + 整个程序的状态），不渲染内层工具名。
- 极简不给紧凑卡加信息：检索词/host 这类更宽的对象只进极简行（`ProgressTool.minimalDetail`），紧凑的 `detail` 仍是「文件名 / 程序名」。

### 入口与开关裁剪

模式行三选一（极简 / 紧凑 / 详细），文本命令 `/display minimal`；极简下 `/display` 卡隐藏所有对它无效的行（思考、截断长度、工具明细、工具输出、紧凑工具行、回合卡步骤、**耗时刷新**），文本报告也只列模式。

## 三、思考块：全文、20 KB 单卡、超长续卡

- **形状**：默认折叠面板（`collapsible_panel`，`expanded: false`）；平铺开关打开时不出现面板，正文直接是卡片元素。
- **内容：全文，永不截断**。不再有「前 200 字 + …(truncated)」这种折叠头。
- **单卡阈值 20 KB（UTF-8 字节）**：折叠面板正文不超过该值时**一张卡不拆**（中文约 6,800 字、英文约 2 万字；飞书整卡 JSON 上限约 30 KB，中文 3 字节/字，20 KB 留足余量）。
- **超过 20 KB**：第 1 片留在面板里，其余发**思考续卡**：
  - 每片同样 ≤ 20 KB；
  - 卡头 `💬 深度思考（续 2/3）`（i18n 新增，`📄 续 n/m` 的思考版）；
  - 发送纪律**与正文续卡完全一致**：等所属步骤卡的 message id 落地后再发（否则续卡会被建在上方）、`prepareCard` 后按序 `channel.send`、上限 30 片、超过上限由 `chunkText` 的 `…(continued)` 尾部标记收束（分片上限，不是内容截断）。
- **分片器**：复用 `chunkText` 的块感知切分（代码块闭合重开、表格重复表头、列表/引用不跨卡），但预算改为**字节**——新增一个按 UTF-8 字节计的入口，而不是把 20 KB 硬换算成字符数（纯 ASCII 会切得过早）。
- 思考块在**简洁模式**不显示（与今天一致），因此续卡只影响详细模式。

## 四、思考预览（默认开，200 字）

| 项 | 规格 |
|---|---|
| 数据源 | `agent/assistant-stream`（宿主进程内事件）的 `frame.chunk.type === 'reasoning-delta'` 的 `text`。**该事件插件已经在订阅**（O20 相位灯，`{ global: true }`），现在只读 `chunk.type` 推进「思考中/回复中/工具」，`text` 被丢弃；预览就是多用这个字段 |
| 权威内容 | 仍然是 `assistant/message`（落定后卡上显示折叠面板全文）；预览只是临时视图，不参与落定 |
| 显示 | 最后 N 字（N = 预览长度，默认 200）+ `🧠 正在思考中…`；显示在**面板之外**（面板收起时也看得见），不改折叠状态 |
| 刷新 | 目标态见第五节（原生逐字流式）；保底态 = 按现有 `elapsedRefreshSeconds`（3/5/10/30 秒，默认 5）刷新一次整卡预览 |
| 消失时机 | `assistant/message` 落地（思考结束）即移除预览元素，卡上只留折叠面板；`frame.type === 'end'` 时同时停止累积 |
| 内存 | 只维护「最后 N 字」的滚动缓冲，不存全文（全文由 `assistant/message` 提供） |
| 写入纪律 | 复用步骤卡更新路径：150 ms 合并、一次在飞、只写最新、送达戳按构建顺序比对（关键坑 45 / 43）；预览写入是**就地更新**，不触发卡片穿插分段 |
| 关闭时 | 预览开关关闭 → 行为与今天完全一致（占位卡 + 相位灯），零回归 |

## 五、逐字流式（打字机）：已真机验证，按额度取舍

### 5.1 机制（平台能力，2026-11-20 实测）

| 环节 | 接口 / 字段 | 实测结果 |
|---|---|---|
| 开启 | 卡片 JSON `config.streaming_mode: true` + `config.streaming_config` | `print_frequency_ms`（默认 70）、`print_step`（默认 1）、`print_strategy`（`fast` = 有新内容立即补齐缓冲；`delay` = 排队播放）。建卡 `code=0` |
| 推文本 | `cardkit.v1.cardElement.content`（元素级、**完整内容** + 单调 `sequence` + 幂等 `uuid`） | 连续 76 次推送全部 `code=0`，无频率拒绝 |
| 收尾 | `cardkit.v1.card.settings` 设 `streaming_mode: false` | `code=0`；**关闭后元素推送被拒 `300309 streaming mode is closed`**，整卡更新仍可用；**重新置回 `true` 后元素推送恢复** |
| 流式中途整卡全量更新 | `cardkit.v1.card.update` | `code=0`，服务端接受；观感上会打断当前动画 |

### 5.2 观感（真机，多轮探针）

| 组合 | 观感 |
|---|---|
| 150ms/字 + 单次大段（#8b） | **匀速、平滑**，但很慢（112 字约 17 秒） |
| 30ms/字 + 单次大段（#9b） | **又快又匀**（190 字约 5.7 秒）——速度完全由 `print_frequency_ms` 决定 |
| 70ms/字 + 每 200ms 推 2 字（#5） | 一段一段、忽快忽停 |
| 70ms/字 + 每 400ms 推 10 字（#6） | 好一些，仍成段 |
| 150ms/字 + 每 400ms 推 10 字（#7） | 仍不匀速 |
| **30ms/字 + 每 1.5 秒推 30 字（#10）** | **目前最好**：接得上、不像分段 |

结论：**客户端不会把多次更新的增量排成一条连续队列；每次元素更新都会重启动画**。要"看起来连续"，必须让**每次推送的增量在两次推送之间正好播完**（`delta_chars × print_frequency ≈ 推送间隔`）。

### 5.3 限制与额度

| 限制 | 数值 | 来源 |
|---|---|---|
| 单卡片实体操作频率 | **10 次/秒**（最小间隔 100ms） | 流式更新卡片概览 |
| `cardElement.content` 接口 | 1000 次/分钟、50 次/秒 | 该接口文档的「接口频率限制」 |
| 单元素内容上限 | **30,000 字符**（超出 `230099/11310`） | SDK 默认常量 |
| 我们自己到 `open.feishu.cn` 的往返 | **200–400ms**（长连接） | 探针实测；**这是真正的瓶颈** |
| API 月度额度 | 按应用、按月计（操作者在后台看到本月已用 6 万次；具体上限未知） | 开放平台控制台 |
| 插件自身计数 | `/status` 的「飞书 API」行（2026-11-20 起） | `src/api-usage.ts` |

**因此可用的推送节奏是 2–5 次/秒，而不是"逐 token"**。而一次思考按 30 秒算：3 次/秒 = 90 次调用、1.5 秒一次 = 20 次、2 秒一次 = 15 次——在月度额度未知的前提下，**默认必须保守**。

### 5.3.1 平台语义：整段替换 + 前缀判定（2026-11-20 查 SDK 文档确认）

`cardkit.v1.cardElement.content` 的 `content` 是**该元素的完整新文本**，不是增量；「分块」只发生在我们**多久推一次**，不发生在传输层。官方文档对输出效果的定义写得很明确（`@larksuiteoapi/node-sdk` 类型声明里带原文）：

> 若旧文本为传入的新文本的**前缀子串**，新增文本将在旧文本末尾继续以打字机效果输出；若新旧文本前缀不同，**全量文本将直接上屏**，无打字机效果。

这解释了我们的两条设计不是偏好而是**必需**：

1. **只能只追加（append-only）**：只要新文本是「旧文本 + 增量」，客户端就只演增量；一旦换成滑动尾部窗口（旧的「最后 200 字」实现），前缀一变，**整段会瞬间上屏**——这正是使用者说的「闪烁 / 刷掉」的平台级原因，不只是高度变化；
2. **单次载荷随文本增长**：每次推的是全文，3,000 字 ≈ 单次 ~9 KB 卡片 JSON，所以预览长度必须封顶（详见上一节）。

卡元素层面确实有 `cardElement.create`（`type: append` 可追加**新元素**）与 `cardElement.patch`（`partial_element` 改属性），但**没有「向文本元素追加一段文字」的接口**；用逐块新元素拼段落会被元素间距、200 元素上限和每实体 10 次/秒拆得不像一段话。所以飞书对读者而言始终是「周期性整段替换 + 客户端动画」的伪流式，真流式只在模型→插件这一段。

### 5.4 实现约定（曾按此实现，2026-11-20 随流式一起移除）

> 本节参数与判据仍然有效，供以后再评估时参考；但当前版本**不发送任何流式更新**。

1. **默认预览节奏：1 次 / 1.5–2 秒**，按「距离上次推送的累积增量」发送（≈ #10 的组合：`print_frequency_ms` 30–50、增量 ≈ 间隔 × 速率）。单步思考约 15–20 次调用。
2. **不提供更快档**，除非同时满足：① 操作者显式打开 `reasoningStreamFast`（新开关）；② `/status` 显示本月额度仍有余量。快档也只到 3–5 次/秒——再快平台不给、网络也不给。
3. **思考结束立即 `card.settings` 关流式**，并用**整卡写入**落定（折叠面板全文 + 正文）；关闭后元素通道即失效（`300309`），这不是缺陷，正好对应"预览只在思考期存在"。
4. **重试可重开**：同一张卡上 `streaming_mode: true` 可以再置回、元素推送恢复，因此 abandoned attempt 退避重试时可以继续在**同一张卡**上打字，不必换卡。
5. **推送必须复用长连接**（插件的 lark SDK 本来 keep-alive）。第一版探针用 `urllib` 每次重新 TLS 握手，单次 1.5–5.5 秒，看起来像"打字机极慢"——这是探针的错，不是平台的。
6. **失败回退**：流式建卡/推送任一步失败 → 关掉流式、按「每 `elapsedRefreshSeconds` 整卡刷新尾部预览」继续，与没有这个功能时行为一致。
7. **额度护栏**：`apiQuotaPerMonth` 设置项 + `/status` 计数（已实现）。后续在预览落地时加一条闸门：本月用量达到配额的 80% 时自动退回「整卡定时刷新」，并在卡片上加一行提示。

**这次迁移会改变思考块的观感**（有意为之，不是回归）：旧 `detailed` 从「前 200 字 + …(truncated)」变成「折叠面板 + 全文」，旧 `standard` 从「首行」变成「折叠面板 + 预览」。**除思考块外**，模式、工具明细、参数、结果、输出截断逐项与今天一致——这是迁移的验收口径。

新增设置键：`reasoningFold`（默认 `true` = 折叠）、`reasoningLivePreview`（默认 `true`）、`toolDetail`（`off|count|summary|full`，旧 `showToolCalls` 布尔读成 `off|full`）、`toolOutputFull`（默认 `false`）；`reasoningPreviewChars` 语义改为预览长度（范围与默认不变）。

## 八、验收与测试点

- **迁移等价**：四个旧档位迁移后，模式 / 工具明细 / 参数 / 结果 / 输出截断的渲染结果与今天逐项一致（单测断言），思考块差异在测试里显式写明；
- **思考形态**：折叠 / 平铺 × 预览开 / 关 四种组合都能渲染；
- **20 KB 边界**：刚好不超 → 单卡一张面板；超一点 → 分片 + 续卡，且每片 UTF-8 ≤ 20 KB、内容不丢；
- **续卡纪律**：顺序（步骤卡落地后）、卡头 `💬 深度思考（续 n/m）`、单片时的写法、30 片上限的收束；
- **预览**：只在思考期出现、按间隔节流（同一间隔内最多一次写入）、`assistant/message` 后消失、关闭开关时零行为变化；
- **旧命令**：`/display tools off`、`/display verbose`、`/display reasoning off` 行为不变；
- **卡面**：`/display` 卡顶层元素 ≤ 16；
- typecheck / 全量测试 / `npm run build` / `npm run privacy` 全绿，一个批次一个 commit。

## 九、不做的边界

- 不改简洁模式的卡片拓扑（回合卡 + 答案卡、纯工具步不发卡）；极简沿用同一拓扑、只换过程卡的形态；
- 极简不新增任何开关：它是第三种模式，不是紧凑模式上的子选项；
- 不删任何档位名，只降级为预设；
- 不碰 DSH WebUI 自己的设置项，只改插件这份配置；
- 不新增「每步卡片是否可见」这类轴；
- 不在本轮改问答 / 审批 / 交付卡片；
- 思考块的名字（深度思考）与折叠文案（点击展开）保持 2026-11-20 已定的样子。
