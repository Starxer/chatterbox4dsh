# 飞书卡片的「流式」试验记录与结论

> 状态：**已放弃（2026-11-20）**。插件不再对任何内容做流式推送；思考块与最终回答都以整卡形式呈现。
> 本文把 2026-11-20 当天的全部试验、平台边界与判断记下来，供以后有人（包括我们自己）想重做时先读一遍。
> 相关实现记录见 [display-modes-design.md](./display-modes-design.md) §5，平台能力见 [feishu-capabilities.md](./feishu-capabilities.md) §2.5。

## 1. 先厘清「流式」在哪一层

| 层 | 是否真流式 | 说明 |
|---|---|---|
| 模型 → 插件 | **是** | DSH 的 `agent/assistant-stream` 逐 token 推 `reasoning-delta` / `text-delta`。 |
| 插件 → 飞书 | **否** | `cardkit.v1.cardElement.content` 每次传的是该元素的**完整新文本**，是声明式替换，不是增量追加，也不是 SSE。 |
| 飞书客户端 → 人眼 | **否** | `streaming_mode` + `streaming_config` 只是让客户端把「新旧文本的 diff」**本地动画**出来。停推就停流。 |

结论：读者看到的「流」= **我们多久推一次** + **客户端打字动画**，属于伪流式。

## 2. 平台语义（决定实现方式的硬规则）

`cardElement.content` 的 `content` 是元素目标态全文。官方文档（`@larksuiteoapi/node-sdk` 类型声明原文）：

> 若旧文本为传入的新文本的**前缀子串**，新增文本将在旧文本末尾继续以打字机效果输出；若新旧文本前缀不同，**全量文本将直接上屏**，无打字机效果。

由此得到三条推论（都在真机验证过）：

1. **追加才有动画**：只推「旧全文 + 增量」才逐字；一旦改成滑动尾部窗口（前缀变了），整段瞬间上屏——这也是早期「预览一闪就没了」的根因，不只是高度变化。
2. **单次推送全文也能有动画**：前提是推之前元素内容为空串或是新文本的前缀。**探针里用 `…` 作占位再推全文，会直接上屏**（2026-11-20 踩到，误判成「20ms 也是直出」）。
3. **没有「向文本元素追加一段文字」的接口**：`cardElement.create`（`type: append`）追加的是**新元素**，`cardElement.patch` 改的是元素属性；用逐块新元素拼段落会被元素间距、200 元素上限、每实体 10 次/秒拆散。

## 3. 参数边界（2026-11-20 真机实测）

| 参数 | 允许范围 | 违规返回 |
|---|---|---|
| `print_frequency_ms` | **≥ 1**（1、2、5、10、20、30、70 均可建卡） | `0` → `code=11311 printFrequencyMs is not complete` |
| `print_step` | **≥ 1**（1、2、3、5 均可） | `0` → `11311 printStep is not complete` |
| 二者必须同时给 | 是 | 只给一个 → `11311 ... is not complete` |
| `print_strategy` | 仅 `fast` / `delay` | 其它值 → `11311 printStrategy is not valid` |

其它相关限制（前次探针，见 [feishu-capabilities.md](./feishu-capabilities.md) §2.5）：每卡片实体 **10 次/秒**；`cardElement.content` **1000 次/分（≈60ms/次）**；单元素 **30,000 字**；关闭流式后再推元素 → `300309 streaming mode is closed`；卡片 10 分钟自动关闭；`update_multi: false` 不支持。

结论：**API 允许 1ms/字**，但人眼有意义的下限是客户端帧率（≈16ms/字，60fps）；真正决定「流得多快」的是**推送频率**，而推送频率又被每实体 10 次/秒（≈100ms）卡住。

## 4. 节奏试验（同一条 1,275 字「思考」文本）

| 编号 | print_frequency | 推送 | 策略 | 观感（使用者反馈） |
|---|---|---|---|---|
| 1 | 8ms/字 | 50 字 / 400ms | delay | 很快，**跟直出差别不大** |
| 2 | 12ms/字 | 50 字 / 600ms | delay | 比 1 稳，仍偏快 |
| 3 | 30ms/字 | 45 字 / 1500ms | delay | 当时线上参数，最稳但慢 |
| 4 | 30ms/字 | 50 字 / 200ms | delay | **积压**：匀速但越来越滞后，结算时被截断 |
| 5 | 30ms/字 | 50 字 / 200ms | fast | 更实时，但**突然追加/跳字** |

判据只有一条：

```
推送间隔 ≈ 每块字数 × 每字毫秒
```

- 间隔**小于**播放时间 → 队列积压（`delay` 匀速滞后、`fast` 跳着追），结算时被整卡写入截掉；
- 间隔**大于**播放时间 → 每块播完空等，出现「顿一下再冲一段」。

另有一个必须知道的限制：**卡片每更新一次，飞书客户端就把会话滚到这条消息的底部**。流式期间读者只能看到最后几行，想从头读必须等它停。这是客户端行为，卡片 API 没有视口/滚动控制项。

## 5. 回答卡单次推送试验（945 字）

| 参数 | 结果 |
|---|---|
| 10ms/字，一次推全文，初始内容 `…` | **直出**（前缀不匹配） |
| 20ms/字，一次推全文，初始内容 `…` | **直出**（同上） |
| 20ms/字，一次推全文，初始内容**空串** | 正常逐字，约 19.4s |
| 10ms/字，一次推全文，初始内容**空串** | 正常逐字，约 9.9s（仍偏快、接近直出） |

即：**单次推送 + 空元素起点**就能拿到打字机效果，服务端只花 1 次调用；但它同样受「自动滚到底部」影响。

## 6. 最终决定（2026-11-20）

**放弃流式，全部整卡呈现。**

理由（按权重）：

1. **思考内容不是交付物**，长度不可预测：短了被结算刷掉，长了要几十秒播完，且每 100ms 一次推送在一步 30 秒思考里会烧掉 200+ 次 API 调用；
2. **自动滚动使流式对阅读是负体验**：打字期间只能看到末尾，无法从头读；
3. **10ms 与直出的观感差别很小**，20ms 才有明显逐字感，而 945 字要 19 秒——比「等结果」更慢；
4. 飞书这条链路无论如何都是伪流式，真流式只在 Web GUI 的 SSE 页面存在。

落地：

- 移除思考期预览（`reasoningPreview` 设置、元素级推送、状态行、结算等待、`streamCardElement` / `closeCardStreaming` 通道方法）；
- 移除 `reasoningPreviewChars`（思考块永远全文，不再有「预览长度」）；
- 思考块保持「全文 + 折叠面板（超 20 KB 走续卡）」，最终回答整卡直出；
- 保留本试验的探针脚本（本机 `~/.dsh/probe-streaming-card.py`、`probe-preview-pace.py`、`probe-answer-stream.py`，不进仓库），要重做时先按本文 §2 的语义与 §4 的判据设计。

## 7. 如果以后还要做，先回答三个问题

1. 推给读者的内容**是不是交付物**？（不是就别流）
2. 它的长度**能不能预估**？（不能就别用固定节奏）
3. 读者**是否需要从头阅读**？（需要就别在飞书里流——自动滚动无法关闭）
